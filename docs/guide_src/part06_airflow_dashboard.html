11. Stage 7: Airflow (running the steps as a workflow)

11.1 What Airflow is, and why it is here

So far you started each step by hand. In real companies, steps must run in the right order, automatically, with retries when something temporarily fails and logs to see what happened. A tool that does this is a workflow orchestrator. We use Apache Airflow.

In Airflow a workflow is a DAG (Directed Acyclic Graph): tasks joined by arrows meaning "this must finish first". "Acyclic" means no loops.

Analogy: a recipe card A DAG is a recipe: "1 chop onions, 2 fry onions, 3 add tomatoes". Airflow is the cook's assistant who follows the card, redoes a step if the stove fails once, and writes down what happened.
Why the stream is NOT an Airflow task An Airflow task must end. A continuous Spark stream (a batch every 5 seconds, forever) never ends. So Airflow runs Spark with --trigger availableNow ("process what is waiting, then finish"), and the replay is limited by a parameter. Say this in the viva: "Airflow orchestrates finite tasks; the endless stream is not a DAG task."

11.2 How it is deployed

  • A custom Docker image (docker/airflow/Dockerfile) based on Airflow 2.10.5 with Java and its own Python virtual environment for our code (so our packages never clash with Airflow's).
  • LocalExecutor (runs tasks as processes on the same machine). Airflow's own bookkeeping lives in a separate database named airflow inside the same PostgreSQL (the streampulse data is untouched).
  • Start: .\scripts\airflow_up.ps1 ⇒ UI at http://localhost:8080, user admin, password = AIRFLOW_ADMIN_PASSWORD in your .env.
  • DAG files: airflow/dags/streampulse_batch_dag.py and streampulse_failure_demo_dag.py.

The failed first run (kept as evidence, and why it matters)

Real failure: "Permission denied" run_spark_available_now failed 3 times (retries working) with java.io.FileNotFoundException: /opt/streampulse/data/checkpoints/orders/offsets/.11....tmp (Permission denied). Cause: the production checkpoint folder was created earlier by the Spark container as the root user, but Airflow tasks ran as a different user who was not allowed to write there. Fix: the Airflow container now runs as root (documented trade-off for a demo; a real system would share one user or use volumes). The other tasks in that run succeeded, and the downstream tasks were marked upstream_failed (they correctly refused to run after a failure).

11.5 The retry and failure demonstration (streampulse_failure_demo)

To show retries, a second DAG runs the real producer against a Kafka address that does not exist (kafka-does-not-exist:9092). This simulates a real outage of a real dependency; no mock service is used.

12.1 How the dashboard works

Start it with .\scripts\run_dashboard.ps1 and open http://localhost:8501. It is three separate pieces:

FileResponsibility
src/dashboard/queries.pyAll database and Parquet access. Every number on the dashboard comes from here. Errors are logged fully for the developer but only a short safe message reaches the user (no passwords, no host names).
src/dashboard/status.pyThe status lights: real checks, not decoration.
src/dashboard/app.pyOnly the screen layout: tables, charts, text.

Rule: no fake green lights A status light is green only if a real check just succeeded. If a service is down it is red; if the check cannot be made it is grey ("unknown"). This was verified by really stopping Kafka and PostgreSQL (section 12.9).

12.9 When services are really down

We stopped the Kafka and PostgreSQL containers on purpose and took real screenshots, then restored them (99,427 rows were intact afterwards).

Overview with Kafka and PostgreSQL stopped: both red; the API light is grey (cannot be known without the database); Parquet and dataset files are still green because those checks really passed.
KPI page with PostgreSQL stopped: "Unavailable: The database is unavailable or the query failed." No technical details leak.
Two dashboard bugs found by LOOKING at screenshots (not by tests) 1. The Kafka light was red while Kafka was running: a client option that this library version rejects raised an error, which my code reported as "down". (My first "down" tests passed for the wrong reason, so a test against the real broker was added.) 2. Three pages printed Streamlit's own documentation: a line of the form st.dataframe(x) if cond else st.write(y) is a bare expression, and Streamlit displays the value of bare expressions. Fixed with a plain if/else, plus an automatic source check. Lesson: always look at the real output.
