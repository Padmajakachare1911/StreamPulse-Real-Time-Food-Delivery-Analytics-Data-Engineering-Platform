5.2 The eight steps

Step 1: read and fingerprint

The orders file is opened and its SHA-256 fingerprint is computed. That fingerprint is used to create the record's identity (step 6).

Step 2: join

Explained in chapter 3 (build_order_rows). Result: one row per order with customer city/state and the item/payment totals.

Step 3: map and convert types (config/field_mapping.yaml, src/common/mapping.py)

CSV values are all text. A mapping file says, for every field: which source column it comes from, its new name, its type, and whether it is required. Excerpt:

config/field_mapping.yaml
  - {source_column: order_purchase_timestamp,      canonical_name: purchase_ts,           type: timestamp, required: true,  origin: orders}
  - {source_column: order_delivered_customer_date, canonical_name: delivered_customer_ts, type: timestamp, required: false, origin: orders}
  - {source_column: items_count,                   canonical_name: items_count,           type: int,       required: true,  origin: order_items}

apply_mapping() converts each value (text → number, text → ISO timestamp such as 2016-09-04T21:15:19) and returns either a clean record or a list of errors. It never crashes on bad data; it reports it. Error codes: MISSING_REQUIRED (a required value is empty) and TYPE_ERROR (e.g. "abc" where a number is needed).

Why a mapping file and not hard-coded names? Rule 7 of the project: never assume column names. The mapping file is built from the real profiled columns, so it can be read, reviewed, and changed without touching code. Spark even builds its message schema from the same file, so producer and consumer can never disagree.

Step 4: validate (config/quality_rules.yaml, src/processing/validators.py)

Nine rules check the order (chapter 9 explains each). If any reject rule fires, the order goes to the dead-letter file with the reason and is not published. The single function classify_record() decides this; the reconciliation script calls the same function, so the two can never disagree.

Step 5: enrich with the API

Chapter 6. Before the loop starts, the producer asks the API once for the BRL→USD rates of the whole date range, then looks up each order's purchase date in that table. If the API is down the producer logs a warning and continues without enrichment (it never stops the ingestion).

src/producer/dataset_producer.py
def make_record_uid(file_sha256_value: str, row_number: int) -> str:
    """Same file + same row => same ID, so a re-run can be recognised downstream."""
    return hashlib.sha256(f"{file_sha256_value}:{row_number}".encode()).hexdigest()[:32]

def make_business_hash(order_id: str) -> str:
    """order_id is a verified natural key (no duplicates in the real orders file)."""
    return hashlib.sha256(f"order_id:{order_id}".encode()).hexdigest()[:32]
Analogy: two kinds of ID record_uid is like the serial number of one photocopy (this file, this row). business_hash is like the title of the document. Two photocopies of the same page have different serial numbers (different record_uid) but the same title (same business_hash).

Step 7: publish to Kafka

producer settings (create_producer)
acks="all"               # wait until the broker confirms the write is safely stored
enable_idempotence=True  # the broker ignores duplicates caused by the producer's own retries
retries=5, retry_backoff_ms=200
linger_ms=20, batch_size=64*1024, compression_type="gzip"   # send in efficient batches
key = order_id           # decides the partition
headers = ingest_run_id, schema_version

Each send returns a "future". Two small callbacks count successes (and which partition got the message) and failures. Every 500 valid records the producer calls flush() and logs progress. Ctrl+C is handled: it flushes what was already sent and still writes the summary.

6. Stage 2: The real external API (Frankfurter)

6.1 What and why

Every order has a money value in Brazilian reais (BRL) and a purchase date. The Frankfurter service publishes official European Central Bank exchange rates for past dates. So we can add: "what was this order worth in US dollars on the day it was bought?"

Why this API? The professor did not name an API (the file docs/inputs/api_info.md does not exist), so we chose one that matches the real columns. Frankfurter needs no key, has no quota, and one request returns about 544 daily rates for the whole 2016-2018 period. A weather API would have needed thousands of calls. Important honesty: public APIs do not contain Olist orders. This API provides reference data, and that is its role.

Reading it: HTTP 200 means "OK, here is your data". 1 BRL was worth 0.31507 USD on 2 October 2017. 2017-10-07 was a Saturday and the ECB publishes no weekend rates, so the program used Friday's rate and labelled it previous_business_day.

6.3 How the client protects us (src/api/client.py)

Timeouts5 s to connect, 30 s to read.Never wait forever.

6.4 How a USD value is attached (src/api/enrich.py)

  1. The lookup key is the purchase date (about 600 different dates), never one call per order. Rule 10: do not call an API 99,441 times.
  2. Exact date found ⇒ fx_match_type = exact.
  3. Weekend or holiday ⇒ use the latest earlier rate (at most 7 days back) ⇒ previous_business_day.
  4. No rate found ⇒ api_enrichment = null (counted, never hidden).
  5. payments_value_usd = payments_value_total × rate, rounded to cents.

Our example order was bought on a Sunday (2016-09-04), so it used the rate of Friday 2016-09-02 (0.30625): 136.23 BRL × 0.30625 = 41.72 USD.
