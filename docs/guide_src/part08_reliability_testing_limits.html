16. Errors, retries, checkpoints and recovery

A data pipeline is judged by what happens when something goes wrong. This chapter collects every protection in one place, then the real failures that were found and fixed.

16.2 Retry, at-least-once and the idempotent sink

Analogy: posting a parcel with tracking If you are not sure the parcel arrived, you send it again. The receiver checks the tracking number: "I already have this one" and throws the duplicate away. Resending is safe because the receiver recognises repeats.
  • At-least-once delivery: after a crash a message may be delivered more than once, never zero times.
  • Idempotent sink: writing the same message again changes nothing. Here, the sink is PostgreSQL with a unique record_uid.
  • Together this gives the effect of "each order counted once" in the warehouse. We never claim "exactly-once".

16.3 Checkpoint recovery: what exactly happens

For each micro-batch Spark writes offsets/N (the plan: "I will read from here to there") before processing and commits/N after it has finished. On restart:

  • offsets/N and commits/N both exist: batch N is finished; the next batch starts after it.
  • offsets/N exists but commits/N does not: batch N was interrupted; it is run again with the same offsets. Its rows may already have reached PostgreSQL, but that is harmless: they are retry duplicates.
real file · data/checkpoints/orders/offsets/0
{"ecommerce_orders":{"0":3338,"1":3345,"2":3315}}

Meaning: the first batch consumed 3,338 + 3,345 + 3,315 = 9,998 messages (partitions 0, 1, 2). Offsets are positions; the numbers are "up to, not including".

16.4 The recovery experiment (isolated checkpoint)

To prove recovery without risking the production checkpoint, an isolated experiment used its own checkpoint, Parquet folder and database tables (04_spark/recovery_test.txt, 07_postgresql/reconciliation_recovery_experiment_r2.txt).

  1. Start Spark on a backlog; let it commit batches 0 and 1; request a safe stop. 4,995 messages stay unread.
  2. While Spark is down, publish 2,000 new orders and 99 repeats of old ones.
  3. Restart. The first batch starts at the committed offset (partition 0 at 1000), not at zero.
  4. Result: Spark consumed 8,094 messages in total; Parquet 8,094 rows, 7,995 distinct; PostgreSQL 7,995; retry duplicates counted 99; 18 of 18 checks passed.

Meaning: nothing was lost (the unread backlog and the new orders were all processed), nothing was doubled in the warehouse (the 99 repeats were recognised), and no old data was reprocessed from scratch.

The failed first attempt (stopping during a batch) is kept as history: 04_spark/recovery_test_attempt1_stop_during_batch.txt.

16.5 Proof that re-ingestion is harmless

On the real production data (99,427 orders) I published the first 200 orders again. Spark consumed 199 messages, inserted 0, counted 199 retry duplicates, and the count stayed 99,427 (07_postgresql/reingestion_production.txt). The two Airflow runs repeated the same proof with 295 messages each.

16.6 Dead-letter queue (DLQ) recap

A DLQ keeps the records you could not accept, with the reason, so they can be inspected and fixed instead of silently disappearing. Two places: data/dead_letter/ingest/ (rejected by the producer: the 14 real orders) and data/dead_letter/stream/ (rejected inside Spark: a malformed message). The real Spark path was exercised by publishing a deliberately broken message (04_spark/malformed_message_test.txt).

17.2 What is mocked and what is real

  • Unit tests may use fake HTTP responses to check the retry logic (that is their purpose; they are labelled as such).
  • Integration and e2e tests use the real services, including the real Frankfurter API. No test pretends to be Kafka or PostgreSQL.
  • One test deliberately checks that the reconciliation tool fails on a real mismatch.
  • A passing test is never presented as more than it is: unit tests are "tested", only saved real outputs are "verified with evidence".

17.3 Status vocabulary

NOT_STARTED → IN_PROGRESS / BLOCKED → IMPLEMENTED_NOT_TESTED → TESTED → VERIFIED_WITH_EVIDENCE. The last one is allowed only when an evidence file exists. See docs/task_tracker.md and docs/evidence_register.md.

18. Limitations (say them before you are asked)

  • Replay, not live. The dataset is history (2016-2018). We replay it into Kafka; we never call these "live orders".
  • The API is not the order source. It supplies the exchange rate. USD values are estimates (weekends use the previous business day: 24,112 orders).
  • At-least-once, not exactly-once; deduplication happens in PostgreSQL.
  • Small infrastructure: one Kafka broker (replication factor 1), one PostgreSQL, Spark in local mode in one container. No monitoring or alerting stack, no schema registry.
  • Parquet is append-only, so it contains repeats; the warehouse is the deduplicated truth.
  • Dataset facts: 775 orders have no items and 1 has no payment (kept and counted); timestamps have no time zone; the licence (CC BY-NC-SA 4.0) was read from a search excerpt and should be re-checked on the Kaggle page.
  • Airflow runs as root in the container (demo trade-off). It orchestrates finite tasks only.
  • Retention: Kafka forgets messages after 7 days; replaying again is safe.
  • Not done by the agent (human actions): the four live demos and their screenshots, confirming the project title with the professor (dataset is e-commerce, not food delivery), asking whether a specific API was expected.
  • Future work: more brokers, a schema registry, alerting, a live source, a cloud warehouse, row-level dashboard drill-down.
