21. Viva questions and answers

Format: short answer first, then the detail. Numbers are the measured ones.

Q1. What does StreamPulse do?

It replays the real Olist e-commerce orders (99,441 rows) into Kafka, processes them with Spark Structured Streaming into a Parquet landing layer and a deduplicated PostgreSQL warehouse, adds a BRL→USD value from the Frankfurter (ECB) API, orchestrates finite steps with Airflow and shows the results on a Streamlit dashboard.

Q2. Is this real-time?

The processing is stream-style (micro-batches every 5 seconds), but the data is historical, replayed. I call it "historical dataset replay", not live orders.

Q3. Why this dataset?

Olist is a real, public, multi-table Brazilian e-commerce dataset (CC BY-NC-SA 4.0) with orders, items, payments, reviews, products and dates: rich enough for joins, quality problems and business KPIs. It is e-commerce, not food delivery, which is why the title was changed and flagged for the professor.

Q4. What is the API and why that one?

Frankfurter: free, no key, ECB reference rates. The professor named no API; BRL→USD fits the data because it has payment values in reais and purchase dates. It is enrichment, not the order source.

Q5. Why Kafka? What are topic, partition, offset, key?

Kafka decouples producer and consumer and stores messages durably so Spark can stop and resume. A topic is a named log (ecommerce_orders); it is split into 3 partitions for parallelism; an offset is a message's position in a partition; the key decides the partition.

Q6. Why order_id as the key?

It spreads messages evenly (measured 33.4 / 33.4 / 33.2 %) and keeps all messages of one order in one partition. customer_state would put 66.9 % into one partition (a "hot" partition).

Q7. Micro-batches and triggers?

Spark Structured Streaming collects new messages into small batches. Trigger 5 seconds runs a batch every 5 s (up to 10,000 messages); availableNow processes what is waiting and stops, which is how Airflow can run it.

Q8. What is a checkpoint and what happens after a crash?

Files recording which offsets each batch will read (offsets/N) and which batches finished (commits/N). After a restart Spark continues after the last committed batch and re-runs an interrupted one. Proven by the recovery experiment: 18/18 checks, no loss, 99 repeats recognised.

Q9. Parquet versus PostgreSQL?

Parquet: compressed columnar files, cheap, append-only landing layer (12 files, 100,120 rows incl. repeats). PostgreSQL: the structured warehouse with constraints and SQL, deduplicated (99,427 rows).

Q10. ETL or ELT?

Mostly ETL for the orders: they are validated and flattened in Spark before the warehouse. Raw payloads are kept in Parquet and the dead-letter files, and the analytics views are computed inside PostgreSQL (ELT-style).

Q11. How do you handle bad data?

Eight rules in config/quality_rules.yaml. Bad records are not dropped silently: they go to the dead-letter queue with a reason code (e.g. INCONSISTENT: 8 delivered-without-date and 6 canceled-with-delivery-date = 14 orders).

Q12. Explain deduplication and idempotency.

record_uid identifies one source row; business_hash identifies one order. The warehouse upsert runs in one transaction and classifies each record as new, retry duplicate (same uid) or source duplicate (same order, different uid). Invariant: attempted = inserted + retry + source. Re-ingesting 199 messages inserted 0.

Q13. Is it exactly-once?

No. It is at-least-once delivery with an idempotent sink, which gives the same result in the warehouse.

Q14. Why is the stream not an Airflow task?

A task must finish; a continuous stream never does. Airflow runs finite steps (including Spark with availableNow) with retries and logs. The real DAG run succeeded 9/9; a real failed run (permission denied) and a failure demo show retries.

Q15. How do you know the dashboard status lights are not fake?

Each light is a real check (a SQL query, Kafka metadata, file listing, HTTP call). When I really stopped Kafka and PostgreSQL the lights turned red and the KPI page showed a safe error.

Q16. Explain lineage and provenance.

Every message carries the source file's SHA-256, row number, run id and API retrieval time. The dashboard shows that all 99,427 warehouse rows come from one file fingerprint (8df58ef3...).

Q17. How do you know the numbers are right?

reconcile.py recomputes expected counts from the source and compares each layer; it exits 1 on an unexplained difference (tested on a deliberate mismatch). Result: all differences zero or explained.

Q18. What went wrong during the project?

Chapter 16.7: winutils, missing JDK, malformed JSON mislabelled, numpy float, Airflow permission, three dashboard bugs, a stop race, a path-length issue and the 14-vs-15 count. Each was diagnosed, fixed and kept as evidence.

Q19. What are the limitations?

Chapter 18 (and 19.6): replay not live, estimated USD, single broker, at-least-once, Parquet repeats, Airflow as root, manual demos pending.

Q20. How would you scale it?

More partitions and brokers (replication factor 3), Spark on a cluster, a schema registry, monitoring and alerting, a managed warehouse, Airflow on Kubernetes.

Q21. Can a user place an order and see it flow through the pipeline?

Yes (chapter 19). The Streamlit page Place a demo order publishes a marked order (source_category = user_demo, id starting demo-) to the same Kafka topic; the unchanged Spark job writes it to Parquet and PostgreSQL; the trace page re-reads each layer for that order id and ticks a stage only when the order is really there. Airflow's availableNow Spark task processes waiting demo orders. Limits: demo orders only, and the dashboard cannot start Spark.

Q22. What are the key numbers?

See Appendix B. Memorise: 99,441 read; 99,427 valid; 14 rejected; 3 partitions; 100,514 Kafka messages; 99,427 in PostgreSQL; 8.11 % late; 100 % enriched.
