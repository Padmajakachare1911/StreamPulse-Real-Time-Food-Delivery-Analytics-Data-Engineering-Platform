19. Placing an order in Streamlit and tracing it (the demo-order extension)

Why this chapter exists The original requirement was: a user places an order in Streamlit and visibly traces it through Kafka, Spark, Parquet and PostgreSQL, with the status on the dashboard and Airflow demonstrated. An audit of the finished project found that the pipeline, Airflow and the dashboard all worked, but the first mile was missing: there was no order form, no producer for user orders, no way to follow one order, and nothing to tell a new order from a historical Olist record. This chapter explains what was added. Step by step with commands: docs/live_demo_order_guide.md.

The Olist data is never changed. No personal data is collected (the customer id is a random demo-customer-...). The Spark job, the Parquet layout and the warehouse schema were not modified.

19.2 How it works

  1. Check the form (state, zip, positive amounts, a non-delivered status; a brand-new order cannot already be delivered).
  2. Build one row in the same shape as the Olist rows and validate it with the real quality rules. Only the purchase-date window (it ends in 2018) uses a demo-only copy that ends today; the historical rules are unchanged and tested.
  3. Ask the real Frankfurter API for the BRL→USD rate (weekends use the previous business day).
  4. Publish with the same producer settings (acks=all, idempotence, key = order_id) and wait for the broker to confirm; log partition and offset.
  5. Spark and the warehouse process it exactly like any other message.

19.3 The trace: four real checks

StageHow it is checked
1 Submittedthe submission log (partition and offset)
2 Kafkaa consumer seeks to that partition and offset, reads the message and compares order_id and record_uid
3 Spark and Parqueta Parquet filter on order_id gives the row and its batch_id; the matching BATCH_SUMMARY line shows how many messages that batch handled
4 PostgreSQLSELECT ... FROM core.orders WHERE order_id = ... (with the same Kafka position)

A stage is ticked only when the order was found there. If Spark is not running, stages 3 and 4 stay "waiting" with the hint to start the stream; if a service cannot be read, the stage says "unavailable", never "done".

  • Duplicate test: sending the identical message again gave Spark batch 16 with inserted 0, retry_duplicates 1; PostgreSQL still has 1 row; Parquet has 2 rows (the landing layer is append-only).
  • Airflow: two orders placed while Spark was stopped showed "waiting". The real DAG run manual__20261016T023952 (success, 9 of 9 tasks) processed them: batch 17 read 3 messages (2 demo orders + 1 historical repeat), inserted 2, retry duplicates 1.

19.5 Problems found while doing it (kept as evidence)

FindingWhat was done
Reconciliation showed +199 unexplained messages that were not demo ordersThe Demo 1 command (--run-id demo1) had been executed twice; the second run overwrote the first run summary. The producer now never overwrites (it adds a suffix such as demo1-2), and reconcile.py detects run-id reuse from Parquet. The expected numbers were not adjusted.
A DAG run stayed queued for 10 minutesThe Airflow scheduler had stopped silently (no error in its log). The container was restarted; airflow_run_dag.ps1 now stops with exit code 3 when the scheduler is not healthy. Root cause unknown.
The "demo orders stored" table lagged behind the traceIt was cached for 30 s; it is now read live.

19.6 Honest limits

  • These are demo orders: no login, cart or payment; item count and totals only (the schema has no product lines).
  • They share core.orders with the historical data; only the KPI views exclude them.
  • The dashboard does not start Spark; it reports honestly whether the order has been processed. Latency of 5 to 10 s is mostly Spark's trigger and batch start-up.

Viva answer: "A user places a marked demo order in Streamlit. It is validated with the real rules, enriched by the real API and published to the same Kafka topic. The unchanged Spark job writes it to Parquet and PostgreSQL, and the trace page re-reads each layer for that one order id, so a stage is ticked only when the order is really there. Airflow's availableNow Spark task processes waiting demo orders too."
