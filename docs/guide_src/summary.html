StreamPulse: Summary

Real-Time Order Delivery Analytics & Data Engineering Platform (Olist Brazilian e-commerce dataset). This is a historical dataset replay through a streaming pipeline, not live orders.

1. Data flow

Olist CSV (9 files) -> Python producer -> Kafka topic ecommerce_orders (3 partitions)
   -> Spark Structured Streaming (Docker) -> Parquet landing layer + PostgreSQL warehouse
   -> Streamlit dashboard (7 pages)        Frankfurter/ECB API adds BRL->USD to each order
   Airflow runs the finite steps (9 tasks, 2 retries); reconcile.py checks every layer

2. What each part does

PartRole and key fact
DatasetOlist: 99,441 orders; orders + customers + items + payments joined with a LEFT JOIN (99,441 in, 99,441 out).
ProducerValidates (8 rules), enriches, publishes with acks=all, idempotence, key=order_id. 99,427 valid, 14 rejected.
APIFrankfurter (ECB rates, no key). 3 tries with 1 s / 2 s waits. 100 % of orders enriched; 24,112 used the previous business day.
KafkaDurable log, 3 partitions, replication 1. order_id key gives an even spread (33.4 / 33.4 / 33.2 %).
SparkMicro-batches every 5 s (or availableNow). Splits valid/invalid, removes in-batch duplicates, writes Parquet and upserts to PostgreSQL. Checkpoint gives crash recovery. Runs in Docker because Windows lacks winutils.
ParquetAppend-only landing layer: 100,120 rows, 99,427 distinct.
PostgreSQLDeduplicated warehouse: 99,427 orders, plus reference tables and 11 analytics views.
AirflowOrchestrates finite tasks only; a stream never ends, so it is not a task. Real run: 9/9 success.
DashboardOverview and status lights, dataset, reconciliation, quality, KPIs, API, recent records. Lights are real checks.

3. Reliability ideas

  • Dead-letter queue: rejected records kept with a reason code (14 real orders: 8 delivered without a date, 6 canceled with a delivery date).
  • Duplicates: record_uid (one source row) and business_hash (one order). Delivery is at-least-once with an idempotent sink, never "exactly-once". Re-ingesting 199 messages inserted 0.
  • Recovery: after a safe stop with 4,995 messages unread, plus new data published while down, restart lost nothing and doubled nothing (18/18 checks).
  • Reconciliation: expected counts recomputed from the source; exit code 1 on an unexplained difference. Result: all differences zero or explained.

5. Honest limitations

  • Replay of 2016-2018 data, not live; USD values are estimates.
  • One Kafka broker, one PostgreSQL, Spark in local mode; no monitoring or schema registry.
  • Parquet keeps repeats; the warehouse is the deduplicated truth.
  • The four live demos and their screenshots are PENDING_HUMAN: you must run them.
