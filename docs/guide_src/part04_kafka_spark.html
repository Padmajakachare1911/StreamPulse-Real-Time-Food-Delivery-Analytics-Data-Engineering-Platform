7. Stage 3: Kafka (the conveyor belt)

7.1 What Kafka does for us

Without Kafka, the producer would have to hand data directly to Spark, and both would need to run at the same speed at the same time. Kafka sits in the middle and stores the messages. The producer can finish and go away; Spark can start later, stop, restart and continue from where it left off, because Kafka remembers every message and its position (offset).

7.2 How the topic is created and kept healthy

  • docker-compose.yml starts Kafka (image apache/kafka:4.1.0, "KRaft" mode: no extra ZooKeeper server).
  • A healthcheck asks the broker for its API versions every 10 seconds; "healthy" means it answers.
  • A one-shot service kafka-init then creates the topic explicitly: --partitions 3 --replication-factor 1.
  • Replication factor 1 = one copy of each message (we have one broker). In production you would use at least 3.
  • Kafka keeps messages for about 7 days by default. After that you would simply replay again (safe, because replays are idempotent).

7.2b Why the key is order_id (a decision measured, not guessed)

The key decides how evenly work is shared. Before publishing we computed (offline, using Kafka's own hash formula) how three candidate keys would spread the real orders:

KeyLane 0Lane 1Lane 2Verdict
order_id (99,441 different values)33.4 %33.4 %33.2 %Even. Chosen.
customer_id33.2 %33.4 %33.3 %Even too, but no benefit.
customer_state (only 27 values)22.2 %66.9 %10.9 %Badly skewed (São Paulo alone is 42 % of orders).

Then, after the real run, we measured on the broker (not just on paper):

Why does order matter inside one lane? Kafka only promises order within a partition. Each order is an independent event, so we do not need orders of different customers in sequence. We just need an even spread, so order_id is perfect. If we had needed "all events of one customer in order", we would have keyed by customer.

8. Stage 4: Spark Structured Streaming (the processing engine)

8.1 Why it runs in Docker

On Windows, Spark needs a helper program winutils.exe to write files. When we first ran Spark on the host it crashed at start-up: HADOOP_HOME and hadoop.home.dir are unset (real log: docs/evidence/00_environment/spark_baseline_existing_stream.txt). The only fix is downloading an unofficial executable, which our rules forbid. So Spark runs in a small Linux container (docker/spark/Dockerfile), reading Kafka through its internal address and writing to the shared data/ folder. Bonus: it works identically on any computer.

8.2 The big idea: process the stream as many small batches

8.3 The files

FileRole
src/streaming/order_stream.pyThe job: reads Kafka, calls process_batch for each micro-batch, handles stopping.
src/streaming/transforms.pyPure DataFrame functions (parse, split, flatten, dedup). Pure = easy to test on small tables.

8.4 What happens inside one batch, step by step

  1. Parse. The Kafka message value is bytes. It is converted to text and parsed with from_json using a schema generated from the same mapping file the producer used. The Kafka position (partition, offset) is kept.
  2. Split valid / invalid. A message is invalid if it is not valid JSON (MALFORMED_JSON) or lacks record_uid / order_id (SCHEMA_MISMATCH). Invalid ones are written to data/dead_letter/stream/ with the original text. (They do not crash the job.)
  3. Flatten. The nested envelope becomes one flat row: envelope fields, typed order fields (timestamps become real timestamps), USD enrichment, original source columns as JSON text, Kafka partition and offset.
  4. Remove duplicates inside the batch. If the same record_uid appears twice in this batch, keep the one with the smallest Kafka position.
  5. Write Parquet. Into its own folder data/processed/parquet/batch_id=00000007/. If the same batch is ever run again, it overwrites its own folder only.
  6. Upsert into PostgreSQL (chapter 10) inside one database transaction.
  7. Log counts. One summary line is logged and appended to data/processed/spark_batches/orders.jsonl.

Spark then writes "batch done" into the checkpoint. Real summary of the very first production batch:

8.5 The checkpoint (Spark's progress notebook)

real folder · data/checkpoints/orders  (never delete this by hand)
commits/   0 1 2 3 ... 13     one tiny file per FINISHED batch
offsets/   0 1 2 3 ... 13     which Kafka offsets each batch was PLANNED to read
metadata                      the id of this streaming query
sources/                      bookkeeping for the Kafka source

offsets/0  last line:  {"ecommerce_orders":{"0":3338,"1":3345,"2":3315}}

How to read it: after batch 0 the notebook says "next time start reading partition 0 at offset 3338, partition 1 at 3345, partition 2 at 3315". If Spark is stopped and started again with the same checkpoint, it reads this and continues exactly there. A batch has an offsets file when it is planned and a commits file when it is finished. If a batch is planned but not committed (a crash), it is simply run again after the restart. That is safe only because our writes are idempotent.

Analogy: a bookmark The checkpoint is a bookmark in a long book (Kafka). If you close the book (stop Spark), you do not start from page 1 again: you open it at the bookmark.
Never delete the checkpoint to "fix" something Without it, Spark would re-read the topic from the beginning (we set startingOffsets=earliest for the first run only). Our scripts that clean up demos are restricted to demo folders and can never touch data/checkpoints/orders.

8.7 Stopping safely (a real engineering story)

Spark has no official "stop between two micro-batches" button. The obvious approach, calling query.stop(), interrupts Spark's thread at any moment, even the instant a batch starts. In our end-to-end test this caused an intermittent failure: an InterruptedException inside a running batch. The data was still correct (the other 17 checks passed) because writes are idempotent, but a "graceful stop" that sometimes is not graceful is not good enough.

The fix is a small protocol (order_stream.py):

src/streaming/order_stream.py (simplified)
STATE = {"in_batch": False, "stopping": False}

def process_batch(batch_df, batch_id):
    STATE["in_batch"] = True              # 1) say "I am in a batch" FIRST ...
    if STATE["stopping"]:                 # 2) ... then look whether a stop was requested
        STATE["in_batch"] = False
        raise StopRequested("batch was not started and will run after the restart")
    ... do the real work ...

# main loop, when the stop file appears:
STATE["stopping"] = True                  # a batch that starts from now on refuses to start
wait until STATE["in_batch"] is False     # a running batch finishes normally
if the query is still active (idle): query.stop()

Because "in batch" is set before the stop flag is read, there is no gap: either the batch sees the stop request and does nothing, or the stopper sees the batch running and waits for it. A batch can therefore never be interrupted while it is writing. The refused batch makes Spark log an error block that contains the word StopRequested; this is the expected signature, followed by the line STOPPED_AT_BATCH_BOUNDARY. After the change, three consecutive recovery runs passed 18 of 18 checks, and the final end-to-end run passed.

What you will see in the demo When you stop Spark, the log may show ERROR lines and a traceback ending with StopRequested: stop requested: batch 3 was not started and will run after the restart. Do not panic: that is the deliberate safe stop. A real problem would not contain StopRequested.
