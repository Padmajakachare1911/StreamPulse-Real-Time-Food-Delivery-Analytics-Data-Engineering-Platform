1. What is StreamPulse, in plain words?

An online shop (marketplace) receives orders all day. Each order has a customer, a status (delivered, shipped, canceled...), dates, money paid, and so on. A company wants to answer questions such as How many orders per month? How much money did we make? How many deliveries were late?

The raw order data is spread over several files and is messy. StreamPulse is the machinery that takes the messy files, cleans and checks them, moves them step by step through a chain of tools, stores them safely, and finally shows the answers on a web dashboard. Building that kind of machinery is called data engineering.

Analogy: a parcel factory Imagine a factory that receives boxes (orders) from a warehouse. A worker opens each box and checks it (validation). Broken boxes go to a "problems" shelf with a note saying what is wrong (dead-letter queue). Good boxes are labelled and put on a conveyor belt (Kafka). Machines at the end of the belt (Spark) sort them into a big archive (Parquet) and into a neat catalogue where each box appears exactly once (PostgreSQL). A manager's screen (the dashboard) shows how many boxes there are. Auditors (reconciliation) count the boxes at every stage to be sure none got lost or counted twice.

1.1 The honest framing: what is real and what is not

QuestionHonest answer
Is the data real?Yes. It is the public Brazilian E-Commerce Public Dataset by Olist (about 100,000 real, anonymised orders from 2016-2018).
Is it food delivery?No. It is e-commerce (many product types). The original project title said "Food Delivery"; we changed the subtitle because the dataset is not food. You should confirm this with your professor.
Are the orders live?No. They are historical. We replay them through a streaming pipeline at a speed we control. Always say: "historical dataset replay through a streaming pipeline".

2. The vocabulary (read this before anything else)

Most confusion in data engineering comes from unfamiliar words. Here are the essential ones, each with a plain explanation. A longer glossary is at the end of the guide.

2.1 About data and pipelines

WordPlain meaningExample in this project
Data pipelineA chain of steps that moves data from where it starts to where it is useful.CSV → Python → Kafka → Spark → PostgreSQL → dashboard
Batch vs streamBatch = process a big pile at once, then stop. Stream = process small pieces continuously as they arrive.Reading the 100,000-order file is a pile; Kafka + Spark treat it as a flow of messages.
Event / messageOne small piece of information that something happened."Order X was placed at 21:15 for 136.23 BRL" is one message.
ReplaySending old recorded data through a system as if it were new.We replay 2016-2018 orders in a few minutes.
ETL / ELTExtract-Transform-Load (clean first, then store) vs Extract-Load-Transform (store first, clean later).Mostly ETL: we check and transform before loading; SQL views do the final analytics.
ValidationChecking that data follows the rules."A delivered order must have a delivery date."
EnrichmentAdding extra information from another source.Adding the USD value from the exchange-rate API.
Provenance / lineageKnowing where every piece of data came from.Each row remembers its source file hash, row number, run id, Kafka position.

2.2 About Kafka

WordPlain meaning
KafkaA system that stores and delivers messages in order, like a very reliable conveyor belt that remembers everything for a few days.
BrokerThe Kafka server (ours runs in a Docker container).
TopicA named channel of messages. Ours is ecommerce_orders.
PartitionA topic is split into several lanes (ours: 3) so work can be shared. Order is guaranteed only inside one lane.
OffsetThe position number of a message inside a lane (0, 1, 2, ...). Like a page number.
KeyA label on a message that decides which lane it goes to. Same key → same lane. Ours: the order_id.
ProducerA program that puts messages into Kafka (our Python replay script).
ConsumerA program that reads messages from Kafka (Spark).

2.3 About Spark and storage

WordPlain meaning
Spark Structured StreamingA tool that reads a flow of data in small groups and processes each group like a mini batch.
Micro-batchOne small group of messages processed together (ours: up to 10,000 messages).
TriggerThe rule for when to run the next micro-batch: every 5 seconds, or availableNow = "process everything waiting, then finish".
CheckpointSpark's progress notebook: which Kafka offsets have been processed. After a stop, Spark continues from there.
ParquetA compact file format for tables, good for analytics. Think "a very efficient Excel file".
Landing layerThe first place data is stored after processing, kept as-is for audit. Ours: Parquet files.
Data warehouseA clean database prepared for questions and reports. Ours: PostgreSQL.
ViewA saved SQL question that looks like a table (e.g. "orders per month").
KPIKey performance indicator: an important number such as revenue or late-delivery rate.

2.4 About safety and correctness

WordPlain meaning
IdempotentDoing it twice has the same result as doing it once. Pressing a lift button twice does not call two lifts.
Upsert"Update or insert": add the row if it is new, skip (or update) it if it already exists.
DuplicateThe same thing appearing more than once. We distinguish retry duplicates and source duplicates (chapter 9).
Dead-letter queue (DLQ)A "problems shelf": rejected records are stored with the reason instead of being thrown away.
At-least-onceEvery message is delivered one or more times; none is lost, but repeats are possible.
Exactly-onceEvery message is processed exactly one time. Hard to guarantee across many systems; we do not claim it.
ReconciliationCounting records at every stage and checking that the numbers agree (or are explained).
Orchestrator / DAGA tool (Airflow) that runs steps in the right order with retries. A DAG is the "recipe": tasks and arrows, no loops.
Container / DockerA sealed, ready-to-run package of a program and everything it needs. Our Kafka, PostgreSQL, Spark and Airflow run in containers.

5.2 The eight steps

Step 1: read and fingerprint

The orders file is opened and its SHA-256 fingerprint is computed. That fingerprint is used to create the record's identity (step 6).

Step 2: join

Explained in chapter 3 (build_order_rows). Result: one row per order with customer city/state and the item/payment totals.

Step 3: map and convert types (config/field_mapping.yaml, src/common/mapping.py)

CSV values are all text. A mapping file says, for every field: which source column it comes from, its new name, its type, and whether it is required. Excerpt:

config/field_mapping.yaml
  - {source_column: order_purchase_timestamp,      canonical_name: purchase_ts,           type: timestamp, required: true,  origin: orders}
  - {source_column: order_delivered_customer_date, canonical_name: delivered_customer_ts, type: timestamp, required: false, origin: orders}
  - {source_column: items_count,                   canonical_name: items_count,           type: int,       required: true,  origin: order_items}

apply_mapping() converts each value (text → number, text → ISO timestamp such as 2016-09-04T21:15:19) and returns either a clean record or a list of errors. It never crashes on bad data; it reports it. Error codes: MISSING_REQUIRED (a required value is empty) and TYPE_ERROR (e.g. "abc" where a number is needed).

Why a mapping file and not hard-coded names? Rule 7 of the project: never assume column names. The mapping file is built from the real profiled columns, so it can be read, reviewed, and changed without touching code. Spark even builds its message schema from the same file, so producer and consumer can never disagree.

Step 4: validate (config/quality_rules.yaml, src/processing/validators.py)

Nine rules check the order (chapter 9 explains each). If any reject rule fires, the order goes to the dead-letter file with the reason and is not published. The single function classify_record() decides this; the reconciliation script calls the same function, so the two can never disagree.

Step 5: enrich with the API

Chapter 6. Before the loop starts, the producer asks the API once for the BRL→USD rates of the whole date range, then looks up each order's purchase date in that table. If the API is down the producer logs a warning and continues without enrichment (it never stops the ingestion).

src/producer/dataset_producer.py
def make_record_uid(file_sha256_value: str, row_number: int) -> str:
    """Same file + same row => same ID, so a re-run can be recognised downstream."""
    return hashlib.sha256(f"{file_sha256_value}:{row_number}".encode()).hexdigest()[:32]

def make_business_hash(order_id: str) -> str:
    """order_id is a verified natural key (no duplicates in the real orders file)."""
    return hashlib.sha256(f"order_id:{order_id}".encode()).hexdigest()[:32]
Analogy: two kinds of ID record_uid is like the serial number of one photocopy (this file, this row). business_hash is like the title of the document. Two photocopies of the same page have different serial numbers (different record_uid) but the same title (same business_hash).

7. Stage 3: Kafka (the conveyor belt)

7.1 What Kafka does for us

Without Kafka, the producer would have to hand data directly to Spark, and both would need to run at the same speed at the same time. Kafka sits in the middle and stores the messages. The producer can finish and go away; Spark can start later, stop, restart and continue from where it left off, because Kafka remembers every message and its position (offset).

7.2 How the topic is created and kept healthy

  • docker-compose.yml starts Kafka (image apache/kafka:4.1.0, "KRaft" mode: no extra ZooKeeper server).
  • A healthcheck asks the broker for its API versions every 10 seconds; "healthy" means it answers.
  • A one-shot service kafka-init then creates the topic explicitly: --partitions 3 --replication-factor 1.
  • Replication factor 1 = one copy of each message (we have one broker). In production you would use at least 3.
  • Kafka keeps messages for about 7 days by default. After that you would simply replay again (safe, because replays are idempotent).

7.2b Why the key is order_id (a decision measured, not guessed)

The key decides how evenly work is shared. Before publishing we computed (offline, using Kafka's own hash formula) how three candidate keys would spread the real orders:

8.4 What happens inside one batch, step by step

  1. Parse. The Kafka message value is bytes. It is converted to text and parsed with from_json using a schema generated from the same mapping file the producer used. The Kafka position (partition, offset) is kept.
  2. Split valid / invalid. A message is invalid if it is not valid JSON (MALFORMED_JSON) or lacks record_uid / order_id (SCHEMA_MISMATCH). Invalid ones are written to data/dead_letter/stream/ with the original text. (They do not crash the job.)
  3. Flatten. The nested envelope becomes one flat row: envelope fields, typed order fields (timestamps become real timestamps), USD enrichment, original source columns as JSON text, Kafka partition and offset.
  4. Remove duplicates inside the batch. If the same record_uid appears twice in this batch, keep the one with the smallest Kafka position.
  5. Write Parquet. Into its own folder data/processed/parquet/batch_id=00000007/. If the same batch is ever run again, it overwrites its own folder only.
  6. Upsert into PostgreSQL (chapter 10) inside one database transaction.
  7. Log counts. One summary line is logged and appended to data/processed/spark_batches/orders.jsonl.

8.7 Stopping safely (a real engineering story)

Spark has no official "stop between two micro-batches" button. The obvious approach, calling query.stop(), interrupts Spark's thread at any moment, even the instant a batch starts. In our end-to-end test this caused an intermittent failure: an InterruptedException inside a running batch. The data was still correct (the other 17 checks passed) because writes are idempotent, but a "graceful stop" that sometimes is not graceful is not good enough.

The fix is a small protocol (order_stream.py):

src/streaming/order_stream.py (simplified)
STATE = {"in_batch": False, "stopping": False}

def process_batch(batch_df, batch_id):
    STATE["in_batch"] = True              # 1) say "I am in a batch" FIRST ...
    if STATE["stopping"]:                 # 2) ... then look whether a stop was requested
        STATE["in_batch"] = False
        raise StopRequested("batch was not started and will run after the restart")
    ... do the real work ...

# main loop, when the stop file appears:
STATE["stopping"] = True                  # a batch that starts from now on refuses to start
wait until STATE["in_batch"] is False     # a running batch finishes normally
if the query is still active (idle): query.stop()

Because "in batch" is set before the stop flag is read, there is no gap: either the batch sees the stop request and does nothing, or the stopper sees the batch running and waits for it. A batch can therefore never be interrupted while it is writing. The refused batch makes Spark log an error block that contains the word StopRequested; this is the expected signature, followed by the line STOPPED_AT_BATCH_BOUNDARY. After the change, three consecutive recovery runs passed 18 of 18 checks, and the final end-to-end run passed.

What you will see in the demo When you stop Spark, the log may show ERROR lines and a traceback ending with StopRequested: stop requested: batch 3 was not started and will run after the restart. Do not panic: that is the deliberate safe stop. A real problem would not contain StopRequested.

9. Stage 5: Data quality, duplicates and the dead-letter queue

9.1 Three promises

  1. Nothing is dropped silently. A rejected record is stored with the reason and the original data.

10.3 The safe write (src/warehouse/load.py)

For every micro-batch, Spark hands the rows to upsert_orders(), which runs inside one transaction (all-or-nothing):

  1. Copy the batch into a temporary staging table (it disappears at the end of the transaction).
  2. Find the known IDs: record_uids already in core.orders or already logged in core.duplicate_records ⇒ these are retry duplicates (counted only).
  3. Among the rest, rank rows by business_hash and keep the first (lowest source row number).
  4. Log the others (or a copy of an order that is already stored) in core.duplicate_records as source duplicates.
  5. INSERT the remaining first rows into core.orders.
src/warehouse/load.py (the invariant that keeps us honest)
accounted = result["inserted"] + result["retry_duplicates"] + result["source_duplicates"]
if accounted != result["attempted"]:      # should never happen; make it loud if it does
    log.error("PostgreSQL batch %s: %d rows attempted but only %d accounted for", ...)

Every attempted row must be accounted for as exactly one of: inserted, retry, or source duplicate. (Seven integration tests on a real PostgreSQL check each case.) Database values are always passed as parameters, never pasted into SQL text (this prevents SQL injection).

Why a transaction? If something fails in the middle of a batch, the whole batch is rolled back: the database never contains "half a batch". Together with idempotency, re-running that batch later gives the correct result.

11. Stage 7: Airflow (running the steps as a workflow)

11.1 What Airflow is, and why it is here

So far you started each step by hand. In real companies, steps must run in the right order, automatically, with retries when something temporarily fails and logs to see what happened. A tool that does this is a workflow orchestrator. We use Apache Airflow.

In Airflow a workflow is a DAG (Directed Acyclic Graph): tasks joined by arrows meaning "this must finish first". "Acyclic" means no loops.

Analogy: a recipe card A DAG is a recipe: "1 chop onions, 2 fry onions, 3 add tomatoes". Airflow is the cook's assistant who follows the card, redoes a step if the stove fails once, and writes down what happened.
Why the stream is NOT an Airflow task An Airflow task must end. A continuous Spark stream (a batch every 5 seconds, forever) never ends. So Airflow runs Spark with --trigger availableNow ("process what is waiting, then finish"), and the replay is limited by a parameter. Say this in the viva: "Airflow orchestrates finite tasks; the endless stream is not a DAG task."

11.2 How it is deployed

  • A custom Docker image (docker/airflow/Dockerfile) based on Airflow 2.10.5 with Java and its own Python virtual environment for our code (so our packages never clash with Airflow's).
  • LocalExecutor (runs tasks as processes on the same machine). Airflow's own bookkeeping lives in a separate database named airflow inside the same PostgreSQL (the streampulse data is untouched).
  • Start: .\scripts\airflow_up.ps1 ⇒ UI at http://localhost:8080, user admin, password = AIRFLOW_ADMIN_PASSWORD in your .env.
  • DAG files: airflow/dags/streampulse_batch_dag.py and streampulse_failure_demo_dag.py.

15. Reconciliation: proving the numbers add up

15.1 The idea

Reconciliation means "count the same thing at every stage and explain every difference". Anyone can print a count; a good engineer shows that nothing was lost or invented. scripts/reconcile.py works from the source: it recomputes what each stage should contain using the same rules, then compares with what is actually there. It exits with code 1 if a difference is unexplained. It never adjusts an expected number to make a row pass.

15.2 Three sections

  1. Run level: each producer run versus the part of the file it covered (read, valid, rejected, published, dead-letter lines).
  2. Source level: unique records over the union of all runs. Runs overlap, so run totals cannot simply be added.
  3. Pipeline stages: Kafka → Spark → Parquet → PostgreSQL.

16.2 Retry, at-least-once and the idempotent sink

Analogy: posting a parcel with tracking If you are not sure the parcel arrived, you send it again. The receiver checks the tracking number: "I already have this one" and throws the duplicate away. Resending is safe because the receiver recognises repeats.
  • At-least-once delivery: after a crash a message may be delivered more than once, never zero times.
  • Idempotent sink: writing the same message again changes nothing. Here, the sink is PostgreSQL with a unique record_uid.
  • Together this gives the effect of "each order counted once" in the warehouse. We never claim "exactly-once".

16.3 Checkpoint recovery: what exactly happens

For each micro-batch Spark writes offsets/N (the plan: "I will read from here to there") before processing and commits/N after it has finished. On restart:

  • offsets/N and commits/N both exist: batch N is finished; the next batch starts after it.
  • offsets/N exists but commits/N does not: batch N was interrupted; it is run again with the same offsets. Its rows may already have reached PostgreSQL, but that is harmless: they are retry duplicates.
real file · data/checkpoints/orders/offsets/0

Meaning: the first batch consumed 3,338 + 3,345 + 3,315 = 9,998 messages (partitions 0, 1, 2). Offsets are positions; the numbers are "up to, not including".

16.4 The recovery experiment (isolated checkpoint)

To prove recovery without risking the production checkpoint, an isolated experiment used its own checkpoint, Parquet folder and database tables (04_spark/recovery_test.txt, 07_postgresql/reconciliation_recovery_experiment_r2.txt).

  1. Start Spark on a backlog; let it commit batches 0 and 1; request a safe stop. 4,995 messages stay unread.
  2. While Spark is down, publish 2,000 new orders and 99 repeats of old ones.
  3. Restart. The first batch starts at the committed offset (partition 0 at 1000), not at zero.
  4. Result: Spark consumed 8,094 messages in total; Parquet 8,094 rows, 7,995 distinct; PostgreSQL 7,995; retry duplicates counted 99; 18 of 18 checks passed.

Meaning: nothing was lost (the unread backlog and the new orders were all processed), nothing was doubled in the warehouse (the 99 repeats were recognised), and no old data was reprocessed from scratch.

The failed first attempt (stopping during a batch) is kept as history: 04_spark/recovery_test_attempt1_stop_during_batch.txt.

16.5 Proof that re-ingestion is harmless

On the real production data (99,427 orders) I published the first 200 orders again. Spark consumed 199 messages, inserted 0, counted 199 retry duplicates, and the count stayed 99,427 (07_postgresql/reingestion_production.txt). The two Airflow runs repeated the same proof with 295 messages each.

16.6 Dead-letter queue (DLQ) recap

A DLQ keeps the records you could not accept, with the reason, so they can be inspected and fixed instead of silently disappearing. Two places: data/dead_letter/ingest/ (rejected by the producer: the 14 real orders) and data/dead_letter/stream/ (rejected inside Spark: a malformed message). The real Spark path was exercised by publishing a deliberately broken message (04_spark/malformed_message_test.txt).

18. Limitations (say them before you are asked)

  • Replay, not live. The dataset is history (2016-2018). We replay it into Kafka; we never call these "live orders".
  • The API is not the order source. It supplies the exchange rate. USD values are estimates (weekends use the previous business day: 24,112 orders).
  • At-least-once, not exactly-once; deduplication happens in PostgreSQL.
  • Small infrastructure: one Kafka broker (replication factor 1), one PostgreSQL, Spark in local mode in one container. No monitoring or alerting stack, no schema registry.
  • Parquet is append-only, so it contains repeats; the warehouse is the deduplicated truth.
  • Dataset facts: 775 orders have no items and 1 has no payment (kept and counted); timestamps have no time zone; the licence (CC BY-NC-SA 4.0) was read from a search excerpt and should be re-checked on the Kaggle page.
  • Airflow runs as root in the container (demo trade-off). It orchestrates finite tasks only.
  • Retention: Kafka forgets messages after 7 days; replaying again is safe.
  • Not done by the agent (human actions): the four live demos and their screenshots, confirming the project title with the professor (dataset is e-commerce, not food delivery), asking whether a specific API was expected.
  • Future work: more brokers, a schema registry, alerting, a live source, a cloud warehouse, row-level dashboard drill-down.

Full list: docs/known_limitations.md.

21. Viva questions and answers

Format: short answer first, then the detail. Numbers are the measured ones.

Q1. What does StreamPulse do?

It replays the real Olist e-commerce orders (99,441 rows) into Kafka, processes them with Spark Structured Streaming into a Parquet landing layer and a deduplicated PostgreSQL warehouse, adds a BRL→USD value from the Frankfurter (ECB) API, orchestrates finite steps with Airflow and shows the results on a Streamlit dashboard.

Q2. Is this real-time?

The processing is stream-style (micro-batches every 5 seconds), but the data is historical, replayed. I call it "historical dataset replay", not live orders.

Q3. Why this dataset?

Olist is a real, public, multi-table Brazilian e-commerce dataset (CC BY-NC-SA 4.0) with orders, items, payments, reviews, products and dates: rich enough for joins, quality problems and business KPIs. It is e-commerce, not food delivery, which is why the title was changed and flagged for the professor.

Q4. What is the API and why that one?

Frankfurter: free, no key, ECB reference rates. The professor named no API; BRL→USD fits the data because it has payment values in reais and purchase dates. It is enrichment, not the order source.

Q5. Why Kafka? What are topic, partition, offset, key?

Kafka decouples producer and consumer and stores messages durably so Spark can stop and resume. A topic is a named log (ecommerce_orders); it is split into 3 partitions for parallelism; an offset is a message's position in a partition; the key decides the partition.

Q6. Why order_id as the key?

It spreads messages evenly (measured 33.4 / 33.4 / 33.2 %) and keeps all messages of one order in one partition. customer_state would put 66.9 % into one partition (a "hot" partition).

Q7. Micro-batches and triggers?

Spark Structured Streaming collects new messages into small batches. Trigger 5 seconds runs a batch every 5 s (up to 10,000 messages); availableNow processes what is waiting and stops, which is how Airflow can run it.

Q8. What is a checkpoint and what happens after a crash?

Files recording which offsets each batch will read (offsets/N) and which batches finished (commits/N). After a restart Spark continues after the last committed batch and re-runs an interrupted one. Proven by the recovery experiment: 18/18 checks, no loss, 99 repeats recognised.

Q9. Parquet versus PostgreSQL?

Parquet: compressed columnar files, cheap, append-only landing layer (12 files, 100,120 rows incl. repeats). PostgreSQL: the structured warehouse with constraints and SQL, deduplicated (99,427 rows).

Q10. ETL or ELT?

Mostly ETL for the orders: they are validated and flattened in Spark before the warehouse. Raw payloads are kept in Parquet and the dead-letter files, and the analytics views are computed inside PostgreSQL (ELT-style).

Q11. How do you handle bad data?

Eight rules in config/quality_rules.yaml. Bad records are not dropped silently: they go to the dead-letter queue with a reason code (e.g. INCONSISTENT: 8 delivered-without-date and 6 canceled-with-delivery-date = 14 orders).

Q12. Explain deduplication and idempotency.

record_uid identifies one source row; business_hash identifies one order. The warehouse upsert runs in one transaction and classifies each record as new, retry duplicate (same uid) or source duplicate (same order, different uid). Invariant: attempted = inserted + retry + source. Re-ingesting 199 messages inserted 0.

Q13. Is it exactly-once?

No. It is at-least-once delivery with an idempotent sink, which gives the same result in the warehouse.

Q14. Why is the stream not an Airflow task?

A task must finish; a continuous stream never does. Airflow runs finite steps (including Spark with availableNow) with retries and logs. The real DAG run succeeded 9/9; a real failed run (permission denied) and a failure demo show retries.

Q15. How do you know the dashboard status lights are not fake?

Each light is a real check (a SQL query, Kafka metadata, file listing, HTTP call). When I really stopped Kafka and PostgreSQL the lights turned red and the KPI page showed a safe error.

Q16. Explain lineage and provenance.

Every message carries the source file's SHA-256, row number, run id and API retrieval time. The dashboard shows that all 99,427 warehouse rows come from one file fingerprint (8df58ef3...).

Q17. How do you know the numbers are right?

reconcile.py recomputes expected counts from the source and compares each layer; it exits 1 on an unexplained difference (tested on a deliberate mismatch). Result: all differences zero or explained.

Q18. What went wrong during the project?

Chapter 16.7: winutils, missing JDK, malformed JSON mislabelled, numpy float, Airflow permission, three dashboard bugs, a stop race, a path-length issue and the 14-vs-15 count. Each was diagnosed, fixed and kept as evidence.

Q19. What are the limitations?

Chapter 18 (and 19.6): replay not live, estimated USD, single broker, at-least-once, Parquet repeats, Airflow as root, manual demos pending.

Q20. How would you scale it?

More partitions and brokers (replication factor 3), Spark on a cluster, a schema registry, monitoring and alerting, a managed warehouse, Airflow on Kubernetes.

Q21. Can a user place an order and see it flow through the pipeline?

Yes (chapter 19). The Streamlit page Place a demo order publishes a marked order (source_category = user_demo, id starting demo-) to the same Kafka topic; the unchanged Spark job writes it to Parquet and PostgreSQL; the trace page re-reads each layer for that order id and ticks a stage only when the order is really there. Airflow's availableNow Spark task processes waiting demo orders. Limits: demo orders only, and the dashboard cannot start Spark.
