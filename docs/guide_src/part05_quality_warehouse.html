9. Stage 5: Data quality, duplicates and the dead-letter queue

9.1 Three promises

  1. Nothing is dropped silently. A rejected record is stored with the reason and the original data.
  2. Empty is not wrong. A missing delivery date is normal for an order not yet delivered. We reject only contradictions.
  3. Repeating is safe. Sending the same data again never creates a duplicate row in the warehouse.

9.2 The rules (config/quality_rules.yaml, src/processing/validators.py)

Each rule was chosen because of something we measured in the real data (chapter 3), not guessed. Severity reject = goes to the dead-letter queue; warn = counted but the order continues.

RulePlain meaningReal result (99,441 orders)
status_in_allowed_setstatus must be one of the 8 values seen in the data0 rejected
purchase_date_in_rangepurchase date must be between 2016-01-01 and 2018-12-310
amounts_not_negativeprice, freight, payment total must be ≥ 00
approved_not_before_purchaseapproval cannot precede the purchase0
delivered_not_before_purchasedelivery cannot precede the purchase0 (used in Demo 3)
delivered_status_has_datestatus "delivered" requires a delivery date8 rejected
delivered_date_matches_statusa delivery date requires status "delivered"6 rejected (all "canceled")

In addition the mapping step rejects empty required fields and wrong types (0 found in the real data). Total: 14 rejected = 8 + 6, which is why 99,441 − 14 = 99,427.

Why these 14 are rejected An order marked "delivered" with no delivery date would break the delivery-time KPI; a "canceled" order that nevertheless has a delivery date contradicts itself. They are not deleted: they sit in the dead-letter files with their full original data, so a human can inspect them.

9.4 The three kinds of "same record" (the most asked question)

KindHow we detect itWhat we do
Retry / replay duplicateSame record_uid (same file, same row)Do nothing; count it as retry_duplicates.
Source duplicateDifferent record_uid but same business_hash (same order_id in two different rows)Keep the first; log the other once in core.duplicate_records.
Re-ingestionSame file ingested again under a new run idSame record_uids, so every record is a retry duplicate: nothing changes.
Analogy: a library returns desk Someone returns a book. If its barcode is already in the "returned" list, you ignore it (retry duplicate). If it is a different barcode but the same title that you already hold, you keep the first and note the second in a "spare copies" list (source duplicate). Otherwise you shelve it (new).
Honest note about the real data The real orders file contains no source duplicates (every order_id is unique). Source duplicates are demonstrated with a small controlled test file (Demo 3). Retry duplicates, however, occur for real: whenever the same orders are replayed (we did it on purpose: 99 + 199 + 295 + ... repeats), and every one was ignored.

10. Stage 6: PostgreSQL (the warehouse)

10.1 The structure

PostgreSQL holds two schemas (folders for tables): core (the real tables) and analytics (views, i.e. saved questions). Created by sql/schema.sql and sql/analytics.sql through scripts/init_db.ps1. This is repeatable: every statement is CREATE ... IF NOT EXISTS or CREATE OR REPLACE, so running it again never deletes data.

10.2 The key table: core.orders

  • Primary key record_uid: no two rows may share it.
  • Unique order_id: the natural key, one row per order.
  • Typed columns: timestamps are TIMESTAMP, money is NUMERIC(12,2) (exact decimals, never floating point), the zip prefix is TEXT to keep leading zeros (e.g. 01037).
  • Provenance columns: source_file_sha256, source_row_number, ingest_run_id, kafka_partition, kafka_offset, processed_at.
  • API columns: fx_rate_brl_usd, fx_match_type, payments_value_usd, api_endpoint, api_http_status...
  • Indexes on purchase time, state and status (they make the dashboard queries fast).

10.3 The safe write (src/warehouse/load.py)

For every micro-batch, Spark hands the rows to upsert_orders(), which runs inside one transaction (all-or-nothing):

  1. Copy the batch into a temporary staging table (it disappears at the end of the transaction).
  2. Find the known IDs: record_uids already in core.orders or already logged in core.duplicate_records ⇒ these are retry duplicates (counted only).
  3. Among the rest, rank rows by business_hash and keep the first (lowest source row number).
  4. Log the others (or a copy of an order that is already stored) in core.duplicate_records as source duplicates.
  5. INSERT the remaining first rows into core.orders.
src/warehouse/load.py (the invariant that keeps us honest)
accounted = result["inserted"] + result["retry_duplicates"] + result["source_duplicates"]
if accounted != result["attempted"]:      # should never happen; make it loud if it does
    log.error("PostgreSQL batch %s: %d rows attempted but only %d accounted for", ...)

Every attempted row must be accounted for as exactly one of: inserted, retry, or source duplicate. (Seven integration tests on a real PostgreSQL check each case.) Database values are always passed as parameters, never pasted into SQL text (this prevents SQL injection).

Why a transaction? If something fails in the middle of a batch, the whole batch is rolled back: the database never contains "half a batch". Together with idempotency, re-running that batch later gives the correct result.
